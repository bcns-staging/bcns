DKIM (DomainKeys Identified Mail) answers a different question than SPF: "has this message's content been tampered with since it left the claimed domain, and did that domain actually vouch for it?" It does this with real public-key cryptography, not IP allowlists -- which is why it survives forwarding (as long as the forwarder doesn't modify the signed parts of the message).

How it works

  1. The sending domain generates an RSA keypair and publishes the public key in DNS at selector._domainkey.domain.
  2. Before sending, the mail server computes a hash of the (canonicalized) body and a chosen set of headers, signs it with the private key, and attaches the result as a DKIM-Signature header.
  3. The receiving server fetches the public key from DNS using the d= (domain) and s= (selector) tags in the signature, and verifies the signature matches.

Try it below: generate a key, sign a message, then look at the exact bytes that got signed. If you change so much as one character of a signed header or the body afterward, verification fails -- that's the whole point.

Canonicalization

Mail servers sometimes make trivial formatting changes in transit (line wrapping, whitespace). DKIM's c= tag chooses how tolerant the hash is of that: simple (byte-exact) or relaxed (normalizes whitespace). This lab uses relaxed/relaxed, the most common real-world choice.
