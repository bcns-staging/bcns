SPF (Sender Policy Framework) answers one narrow question: "is this IP address allowed to send mail claiming to be from this domain?" It works by publishing a DNS TXT record listing authorized senders.

✉️
Message Arrives
From IP 203.0.113.10, envelope-from alice@domain.com
→
🔍
Look Up SPF
Fetch TXT record for domain.com
→
📋
Check Mechanisms
Is 203.0.113.10 in the allowed list?
→
PASS
IP is authorized
FAIL / SOFTFAIL
IP is not authorized

How it's actually checked

When a mail server receives a message, it looks at the envelope sender (the MAIL FROM address used during the SMTP conversation -- not necessarily the From: header the recipient sees), takes its domain, and fetches that domain's SPF TXT record. It then evaluates the listed mechanisms, in order, against the connecting IP address.

MechanismMeaning
ip4:1.2.3.4Matches a specific IPv4 address or CIDR block
aMatches any IP the domain's own A/AAAA record resolves to
mxMatches any IP of the domain's mail servers (MX records)
include:otherdomainRecursively evaluates another domain's SPF record (common for third-party senders like marketing tools)
allMatches everything -- always placed last as the catch-all

Each mechanism has a qualifier: + (pass, default), - (fail), ~ (softfail), ? (neutral). Most real records end in -all (strict) or ~all (lenient, still delivers but marks it).

Why SPF alone isn't enough

SPF checks the envelope sender, which the recipient never sees -- it checks nothing about the visible From: header, and it breaks completely when a message is forwarded (the forwarding server's IP isn't in the original sender's SPF record). That's exactly why DKIM and DMARC exist.
