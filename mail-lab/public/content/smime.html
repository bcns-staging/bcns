S/MIME secures message content rather than transport or sender identity checks: it signs and/or encrypts the message body itself using X.509 certificates -- the same certificate technology used for HTTPS. A signed message proves the content hasn't been altered and came from whoever holds the matching private key; an encrypted message can only be read by whoever holds the matching private key.

In production, S/MIME certificates are usually issued by a trusted Certificate Authority (the same CAs that issue HTTPS certificates), so a recipient's mail client can validate the chain of trust automatically. This lab uses self-signed certificates instead -- real crypto, but you're your own CA, exactly like the "this connection is not private" warning you'd get visiting a site with a self-signed HTTPS cert.

Simplification note: real S/MIME wraps the signature in a full CMS/PKCS#7 ASN.1 structure carrying the certificate chain. This lab performs the same certificate generation and RSA-SHA256 signing/verification with real cryptography, presented in the same multipart/signed MIME shape, but without the full ASN.1 encoding -- the concepts and trust mechanics are identical.
