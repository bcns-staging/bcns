Email headers are separated by CRLF (\r\n). If application code builds a header value by directly concatenating unsanitized user input -- say, a web form's "subject" field passed straight into an email header -- and that input contains a raw CR or LF character, a naive parser reads everything after the newline as a new header, not part of the original value.

⌨️
User Input
"Order confirmation\nBcc: attacker@evil.com"
→
🧩
Naive Concatenation
Dropped straight into "Subject: " + input
→
Unsanitized
Parser sees TWO headers — forged Bcc smuggled in
Sanitized
CR/LF stripped — stays ONE header

This is directly analogous to SQL injection or HTTP response splitting: the vulnerability class is "attacker-controlled data crosses into a control-plane position because a delimiter wasn't stripped or escaped." Historically, this let attackers inject an extra Bcc: to silently copy themselves on outgoing mail, or even smuggle an entirely new MIME part.

The fix is simple and absolute: never allow raw CR or LF characters into a header value. Strip them, reject them, or encode them -- never pass them through.
